# 下一阶段实施计划：从文字成稿到可发布笔记

2026-10-02。基于当前代码核对，范围为 T1–T5 的规划；本文件没有表示这些功能已实现。入口说明见 `handoff-next-steps.md`，真实发布和回采证据见 `publish-smoke-test.md`。

## 目标与顺序

第一阶段交付：选题一键成稿 → 自动带封面 → 可补自己的图片、排序 → 创建发布任务。第二阶段再让账号风格和真实表现影响创作。

| 次序 | 切片 | 依赖 | 完成信号 |
|---|---|---|---|
| 持续核对 | T0 回采 | 已发 #13、插件在线 | verified 与首条真实指标快照已通过；1 天/7 天待到期 |
| 1 | T1 图片上传与草稿素材保存 | 无需等 T0 | 3 张自己的图片进入草稿，私密发布的图序正确 |
| 2a | T2 中文封面渲染与任务 | T1 存储与素材契约 | 4 个模板输出 1080×1440 PNG，中文完整可读 |
| 2b | T2 一键成稿与封面编辑 | 2a | 一键成稿后自动带首图，可改字、换模板、重生成 |
| 3 | T3 账号人设 | 创作链路稳定 | 两个账号的定位/风格/红线分别生效，心跳不覆盖它们 |
| 4a | T4 洞察与单篇复盘 | T0 首条快照 | 显示实际采样时间、缺失指标与复盘证据 |

| 5 | T5 自动浏览采集 | 当前采集管道 | 搜索任务可暂停恢复，遇验证暂停，重启不重复入库 |

T1–T3 可在等待回采期间推进。T4 的契约、查询和空态可先准备；评分校准不得由当前一篇私密测试笔记得出。T5 先落小范围试跑，原规划的作者任务、推荐页和高级条件分后续切片。

## 当前代码里的实施约束

1. `app.ts` 将整个 `mediaModule` 放在无鉴权区域。上传和素材状态查询必须在 `secured` 下注册；对象读取继续兼容 `<img>` 与插件下载。
2. `topics.ts` 的 AI `to-draft` 仍同步等待模型，生成的 `cover` 仅以 `coverText` 返回，草稿内没有持久化。T2 要同时处理异步成稿、封面状态与幂等。
3. `drafts.tsx` 的 900ms 自动保存会发送 title/content/tags/images 全字段快照。后台新增封面或上传完成时，旧快照可能把新图覆盖。T1/T2 必须解决编辑与后台回写冲突。
4. `media-store.ts` 的 GC 有 10 分钟宽限期，但容量超限时会删除仍被引用的对象。新上传和生成的创作素材必须有独立的保留规则。
5. `media-jobs.ts` 已有 `queued/processing` 的服务端任务状态；插件领取 `pending/running`。当前 `/ext/tasks/pending` 未限制 type，增加任务时必须保持执行方边界。
6. schema 的结构变更还要同步 `db/migrate.ts` 的幂等 DDL。开发验证用 PGlite，不能在正在连生产库的服务上启用启动迁移。

## T1：上传自己的图片

### 产品范围

草稿图片区提供选择和拖放、多张队列、逐张状态、失败重试、排序与移除；保留粘贴 URL。排序同时提供可用的前移/后移按钮。上传中不能把本地 `blob:` 地址保存成正式发布素材。

建议起始限制：单图 10MiB、JPEG/PNG/WebP、解码后像素总数不超过 40MP。限制是本产品配置，实施时核对插件与平台能接受的张数，并统一前后端上限。实际解码识别类型，校正 EXIF 方向并去掉定位等元数据；不靠文件扩展名或浏览器 MIME 判定。

### 存储与契约

- 先在 `packages/shared` 定义 `MediaAsset`、上传请求/响应和图片关联字段；`NoteImage` 的新增字段保持可选，兼容历史粘贴 URL。
- 新增 `media_assets` 元数据：userId、所属 draftId、kind（upload/cover）、status、key、contentHash、size、width/height、createdAt、error；包含任务关联和上传批次的稳定顺序。
- 拟定 `POST /api/media/upload`：Bearer + multipart（file、draftId、批次/幂等标识），校验草稿归属后接收，返回 `202 {assetId,status}`。`GET /api/media/assets/:id` 仅当前用户可读，ready 才有正式 URL。草稿查询能恢复未完成上传队列。
- 外部 R2 写入进 jobs；接收后源文件暂存到可持久恢复的 `DATA_DIR/uploads`，配数据库记录。该目录在部署 rsync 排除的 `apps/server/data` 下；配置自定义目录时要确认不会被部署删除。服务重启能重排，R2 确认成功后清理暂存。不能把暂存路径当最终素材 URL。
- 未配置 R2 时返回可识别的 `503 storage_unavailable`，页面保留 URL 入口；不接受文件后假装上传成功。开发用 mock R2，真实上传验收使用独立测试配置和明确归属的草稿。
- 对象建议使用 `upload/<64hex>`、`cover/<64hex>`，哈希按用户范围与最终内容计算，跨用户没有素材管理权限。对象 key/状态查询不暴露桶列表。复用 `publicBase` 返回对插件可达的绝对 URL。
- `mediaModule` 扩展对象路径白名单；新目录避免旧版 GC 扫描，同时新版 GC 汇总所有前缀容量。禁止以腾空间为由删除仍被草稿/发布引用的创作图片；容量不足就拒绝新上传/生成并显示原因。
- 移除草稿图片仅解除关联；没有其他引用的资产经过宽限再回收。不直接删除可能被其他草稿引用的哈希对象。

### 并发与发布

- 每张上传绑定发起时的 draftId，切换草稿后不能插入新草稿；顺序由用户选择/排序决定，不能按后台完成顺序追加。
- 用户移除正在上传的项后，完成回调不能把它加回来。服务端保存取消/关联意图，重启恢复遵守它。
- 自动保存改为只提交实际变更字段；图片更新增加版本检查，后台回写在事务中合并当前图集。冲突时重新读取并显示处理结果，避免旧 images 覆盖新素材。
- 新建发布任务前落盘当前编辑，校验正式素材 ready；封面/上传失败不能以“有图片占位”通过。待发布/执行中的图集应冻结素材引用，避免后续编辑影响已排任务。
- 验证开发与生产插件构建的 `host_permissions`，并走真实 `FETCH_IMAGE` 验证 objects URL、MIME 与图序。本地 API 在不同端口时不能生成插件无权限抓取的地址。

### 文件与验收

修改：`packages/shared/src/types.ts`、server `app.ts`、`modules/media.ts`、`modules/drafts.ts`、`modules/publish.ts`、`db/{schema,migrate}.ts`、`lib/{r2,media-store,media-jobs}.ts`、web `lib/api.ts`、`pages/drafts.tsx`；必要时扩展插件发布载荷。上传 UI 可复用 vendored `components/motion/file-upload.tsx`。

必要验证：未授权/跨用户拒绝、伪造类型/损坏图/超限、R2 未配置与失败、进程重启、重复提交、切草稿、乱序完成、移除后迟到回调、编辑冲突、GC 保留。真实验收为 3 张不同图片上传并排序后，以 private 发布成功，平台图序一致。

## T2：模板化文字封面

### 首版效果与模板选择

默认按来源爆款的可用封面描述选模板，无描述则用红白文字卡片；草稿可主动换模板。用户对本轮风格问题的回复优先于此默认。只借鉴版式、信息层级，不自动使用采集到的原作者图片。

| 模板 | 适用内容 | 必要输入 | 缺少输入时 |
|---|---|---|---|
| 大字海报 | 观点/提醒/短钩子 | 主标题 | 通用兜底 |
| 清单步骤 | 有明确步骤/要点 | 主标题、2–4 个真实要点 | 回退大字海报，不编步骤 |
| 前后对比 | 有明确的对比关系 | 主标题、两组短标签 | 回退大字海报，不编效果数字 |
| 照片标题条 | 用户有自己的底图 | 主标题、用户素材 assetId | 回退文字模板 |

固定输出 1080×1440 PNG。模板里字号、留白、行数有明确上限；长中文、中英混排、标点、无底图必须可读。用户底图仅取本人 ready 素材；原图/文字都与笔记主题一致，文字不添加未经依据的功效、数字或承诺。

### 渲染与状态

- 优先验证现有 `sharp` 的文字图层 + 图形合成，不先引入另一套大型渲染依赖。先完成 Windows/Linux 中文渲染小样；若部署构建不支持所需文字能力，再评估专用 renderer。
- 打包一款 Noto Sans CJK SC 的固定字重与完整许可文件，指定 fontfile，不能靠生产机系统字体。文字转义后再用于 Pango markup；颜色/布局来自模板定义，不让任意输入变成 SVG 或富文本。
- 草稿持久化 coverSpec：headline、templateId、要点/对比文案、backgroundAssetId、templateVersion；另存 coverState、activeAssetId、revision/error。旧草稿均可读。
- 生成使用 `cover_generate` 服务端 job。对象内容哈希包含最终输出，任务幂等键含 draftId + spec revision；旧任务完成不能覆盖新参数或用户已删除的封面。
- 生成成功写入 `draft.images[0]`。重新生成只替换系统封面，保留用户上传图与其顺序；生成失败保留旧可用封面，并给出重试入口。
- 新增 `POST /api/drafts/:id/cover`（202，返回任务与 coverState）；草稿详情返回状态供页面轮询。无 R2、无字体、无可用标题分别返回清晰原因。

### 一键成稿接入

`to-draft {ai:true}` 改为先创建并绑定草稿与持久任务，立即返回 202；worker 完成文字 → 保存 coverSpec → 渲染并存 R2 → 标记完成。成稿与封面有独立进度和错误，用户可以重试失败步骤。手写转草稿保持原行为；已有绑定草稿继续幂等返回。

同一选题并发点击只创建一份草稿/成稿任务。成稿期间用户修改正文时，后台不能无条件覆盖；发布按钮根据当前正式图集与生成状态显示可用性。所有慢操作仍由 server jobs 执行，不能被插件领取。

新增候选文件：`lib/cover-render.ts`、`lib/cover-templates.ts`、`lib/draft-jobs.ts`、字体目录；修改 `draft-gen.ts`、`topics.ts`、`index.ts`、schema/DDL、shared 契约、web topics/drafts/API。生成调度尽量复用已有 claim/retry 模式，不建立另一个队列系统。

验收：4 个模板逐张视觉检查，包括长标题/换行；自动化验证尺寸、参数校验、断点恢复、过期任务、图片保留和幂等。真实链路从选题成稿开始，无需粘贴图链或手工补封面即可创建发布任务，私密发布首图正确。

技术依据：[sharp 图层与 fontfile 文档](https://sharp.pixelplumbing.com/api-composite/)；[Noto CJK 项目](https://github.com/notofonts/noto-cjk)；[字体许可](https://raw.githubusercontent.com/notofonts/noto-cjk/main/Sans/LICENSE)。正式选用时固定字体版本并附版权/许可，不依赖运行时下载。

## T3：账号定位、风格与红线

- schema/DDL 加 `positioning`、`styleNotes`、`redlines`，默认空；`PATCH /api/accounts/:id` 仅修改人设字段、校验归属和长度。心跳只更新账号识别/在线字段，不覆盖人设。
- 账号矩阵提供三个编辑字段，独立保存；后续可给分析得出的风格建议，首版不自动回写用户人设。
- 选题生成/深评读取目标账号；成稿默认读取 topic.accountId；分析增加可选 accountId，并记录本次人设快照。无账号时按通用风格生成；一次性 positioning 允许覆盖本次定位，但不能隐式取消账号红线。
- 统一 `account-persona` 提示词构造函数，注入选题、成稿、分析，避免三套互相不一致的字段解释；顺带覆盖草稿 AI 改写。
- 自然语言 redlines 用于模型自查并展示风险；它不是能够自动精确匹配的禁词列表。确定性拦截继续用已有违禁词机制；若要账号自定义硬禁词，另设明确的词条契约，不能承诺任意描述都可被硬校验。
- 发布选择的账号可能与选题账号不同。发布前按实际目标账号重新检查人设红线，给出冲突/风险提示；不默默套用另一个账号的规则。
- 文件：shared types、schema/DDL、accounts.ts、ext.ts 心跳回归、ai.ts、draft-gen.ts/draft-jobs、collections.ts/analysis-run、web accounts/AI 入口。
- 验收：两个账号在相同素材下输出各自风格；记录的快照可追溯；跨用户 accountId 拒绝；修改人设不改变历史报告；下一次心跳不覆盖编辑值。

## T4：先消费数据，再校准选题

### 首版洞察与复盘

规划 `GET /api/insights/overview`、`/notes`、`/notes/:jobId`；按账号/时间筛选，使用每篇最新快照或明确时点的快照，不把累计快照加总为总互动。

展示粉丝/获赞/发文趋势、已发笔记表现榜、单篇曲线、采样时间与延迟。missing/null 与真实 0 分开；只有互动数时曝光、浏览和互动率不可计算，界面写“未采到”。目前 metrics 主要打开 www 详情，不能假定一定能拿到创作中心曝光/浏览量。

`POST /api/ai/postmortem {publishJobId}` 创建异步持久报告，读取实际正文、封面参数、人设快照和指标时间序列；结构为证据、可能原因、缺口、下一篇实验建议。数据不足就报告不足；没有曝光不得断言点击率，私密笔记单独标记并默认排除效果榜。

### 评分对照与后续校准

- 发布前冻结该选题的 score/scoreDetail、评分口径/模型版本、人设、内容快照，避免发布后修改评分污染历史比较。先核对选题到多个发布任务的关联，不能只依赖 topic 最后一次 publishJobId。
- 用实际发布时间至 capturedAt 的年龄分组比较 1h/24h/7d 表现，记录延迟与采样来源；晚到快照不能标成准点快照。
- 先展示分数分组、样本数和各指标中位数/分布。账号、私密状态、内容类型及投放等因素不足时保留缺口，跨账号大号/小号不直接混排。
- 流量潜力可以与真实互动/曝光对照；账号匹配、变现、成本、合规等维度不能仅凭点赞推断。先保留人工建议和版本记录，积累可比样本后再评估是否修改权重/提示词。
- 一个或少数样本只显示观察，不自动调整模型。具体样本阈值、目标指标、验证集在看到数据覆盖后确定，避免写一个无统计依据的“足够样本”数字。

文件：shared、新增 insights module、postmortem worker/report schema、publish.ts 的快照、web insights/单篇详情/导航、已有图表组件。验收重点是按用户隔离、快照不重复加总、时点选择、私密排除、空/缺失数据、复盘无依据时不编结论。

## T5：先验证关键词任务，再扩展作者任务

- 首切片只支持一个关键词 → 站点搜索页 → 有限滚动 → 点赞过滤 → 详情/评论 → 指定库；规则、库、扫描/入库/评论上限和间隔在创建时冻结。
- server 保存任务和逐篇进度；插件仍是执行方。全浏览器共用有容量的串行队列，主动采集与回采/发布协调，发布与到期回采优先，避免任务互相抢标签页和请求节奏。
- 新任务领取协议必须带能力/类型过滤，旧插件不能误领无法执行的新类型。类型/桥协议先定义在 shared；XHS 动作放平台适配代码，纯字段解析继续走 shared。
- 任务状态包含 queued/running/paused/blocked/done/partial/failed/canceled；篇级发现/跳过/待详情/已保存/待评论分别记录。SW 重启用持久 checkpoint 恢复，孤儿页回执不能当新任务结果。
- 登录失效、验证码或拦截时全队列暂停并引导用户处理；不自动绕过验证。取消后迟到的响应不得继续新增入库。
- 任务页关闭普通浏览自动采集，避免递归或重复计数；评论总量/实采主评/实采回复分别展示。仅收到一页评论不能标全量完成。
- 无更多结果、重复无增量、触及扫描/入库上限或持续超时都要明确结束原因。作者主页任务复用上述机制；推荐页与高级热度条件随后增加。
- 验收：有限关键词真实试跑、暂停/继续/取消、浏览器关闭/SW 重启、跨用户隔离、队列溢出、验证码、重复嗅探、迟到回执；随后检查实际有效入库数和评论覆盖，而不是只看任务 done。

## 实施与发布检查

当前本地 3000 服务继续用于 T0，连接生产库且关闭迁移/媒体 worker。实现 T1 起使用独立 PGlite 配置和端口，避免修改 `.env` 或热重载中的生产连接服务后误写数据；测试用注入 mock AI/R2，不连接外网。

建议切成 T1、T2a、T2b、T3、T4a、T4b、T5 多个可审查变更。每片先 shared 契约，再 server/DDL，最后 web/extension，更新 `docs/api-contract.md`。生产需要新版 objects 路由后才能使用新素材 URL；上传临时目录、字体包和相关配置要进入部署核对。

代码阶段执行 `npm run typecheck`、`npm test`、`npm run build:ext`；修改 web 或部署素材时还执行 web build。真实发布测试全部 private，保留生产测试痕迹，记录具体任务和平台结果。本轮仅形成计划，没有改接口、执行迁移、发布新笔记或推送 main。
